Data quality

The dataset's own soft spots, stated rather than smoothed over.

What the dataset knows is questionable about itself. None of this is corrected silently: rewriting a filer's own disclosure would be worse than reporting it with the caveat attached.

Alias choices that stopped holding

Which XBRL tag a filer means by "total proved reserves" is chosen by measurement, not by a global default: developed + undeveloped = total is an identity that a combination of tags either satisfies or does not. These filers have no combination that satisfies it, or had one that stopped working — the tag kept its name and changed its meaning.

Reserve arithmetic that does not add up

Proved developed reserves are a subset of total proved, so developed can never exceed total and both must be quoted in the same unit. This is the cheapest check on the scale-label problem because it needs no outside knowledge of how big a company is — it compares one filer's numbers against its own. The sum check is the one that catches a wrong alias: when developed and undeveloped agree with each other but not with the total, it is the total's tag that does not mean what it appears to.

Unit discontinuities

Series where the filer changed the declared unit partway through. Devon tags total proved reserves as MMBoe through FY2022 and MMcfe from FY2023 while the values run continuously — a real BOE-to-cfe change would move the figure about sixfold, so the later label is wrong.

Fallback tags

Cells filled from a less specific XBRL tag because the filer did not tag the precise concept. RevenueFromContractWithCustomerExcludingAssessedTax is total revenue, not oil and gas revenue — comparable only with that difference stated.
